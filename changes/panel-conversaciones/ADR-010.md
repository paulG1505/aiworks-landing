# ADR-010: Consola de Conversaciones con Login en la API Pública

**Status:** Accepted (2026-10-28, Paul)
**Fecha:** 2026-10-12

## Context

Con el número de WhatsApp de `aiworks` migrado a la API (sin app de WhatsApp Business), Paul ya no
tiene dónde ver cuántos chats atiende el bot ni cómo responde. Hoy el admin (`/admin/metricas`,
`/admin/sesiones/...`) corre solo en `127.0.0.1:8001` dentro del contenedor, Caddy no lo proxya, solo
cubre sesiones web y no muestra texto de WhatsApp. Se consulta por SSH.

Paul decidió que la consola viva **dentro de la landing** (`aiworks.lat/consola`), con login, y que el
login siempre se valide contra el back. La landing es un export estático en GitHub Pages
(`output: "export"`), así que no puede guardar sesiones ni secretos: toda autenticación va en la API.

## Decision

1. **El admin loopback no cambia.** `/admin/recargar` y el resto siguen solo en `127.0.0.1:8001`.
2. **Un router nuevo `/console/api/*` en la app pública** (`api.aiworks.lat`), que Caddy sí proxya. Es
   de solo lectura salvo `login` y `logout`.
3. **Un solo usuario**, definido por variables de entorno: `CONSOLE_USER`, `CONSOLE_PASSWORD_HASH`
   (argon2id) y `CONSOLE_TOTP_SECRET`. Sin `CONSOLE_USER` o sin hash, el router responde 404: la
   consola nace apagada.
4. **Login con contraseña y TOTP.** La sesión es un token opaco aleatorio guardado como hash en
   SQLite, con caducidad. Viaja en una cookie `HttpOnly; Secure; SameSite=Strict`. Sin JWT ni
   `localStorage`.
5. **Cada petición valida la sesión en el back** mediante una única dependencia `require_admin`. Es el
   punto único donde, si algún día hay roles o vistas por tenant, entra una librería de autorización
   (Casbin u otra). No se adopta ahora: con un usuario y un rol no protege nada.
6. **CORS con credenciales solo para `https://aiworks.lat`** y solo en `/console/*`. La landing y la
   API son del mismo sitio (`aiworks.lat`), por lo que la cookie `SameSite=Strict` viaja.
7. **Tabla `metricas_diarias`** (tenant, canal, día, chats nuevos, listos para llamada), alimentada
   cada día antes de la purga. Sin texto ni teléfonos. `uso` ya conserva respuestas y costo.
8. **Teléfonos enmascarados** en toda respuesta de la consola. No existe endpoint para verlos completos.

## Consequences

### Positivas

- Paul ve chats de WhatsApp y web desde cualquier dispositivo, sin SSH.
- El admin con acciones (`recargar`) sigue sin tocar internet.
- La tendencia mensual sobrevive a la purga de 30 y 60 días sin guardar datos personales.
- `require_admin` deja un punto único para añadir roles después.

### Negativas

- **Se abre superficie pública nueva con conversaciones de clientes detrás de una sola puerta.** Una
  contraseña débil o un TOTP robado entregan todo. Se mitiga con argon2id, TOTP, bloqueo por intentos
  y registro de accesos, pero el riesgo existe y antes no existía.
- **El código del panel es público**: vive en el repo público de la landing. Es válido porque no lleva
  secretos y los datos solo salen de la API autenticada, pero no es el repo privado que Paul quería.
- **Rompe el invariante «Caddy nunca proxya el admin»** solo en apariencia: lo que se proxya es un router
  distinto y de solo lectura, no el admin loopback. Hay que dejarlo escrito en el `CLAUDE.md` del
  producto para que nadie mueva `recargar` ahí.
- Una dependencia nueva para el hash (`argon2-cffi`) y otra para el TOTP (`pyotp`).
- Si el único usuario pierde su autenticador, la recuperación es manual: regenerar el secreto por SSH.

### Neutras

- La política de retención (30 y 60 días) no cambia; el panel solo muestra lo vivo.
- La consola no escribe nada del negocio: no responde, no borra y no edita conversaciones.
